## 백지 인출 (내 답)

### Q1. `int[]`(배열)는 왜 크기가 고정인가? (메모리 관점에서)
컴퓨터의 메모리는 연속된 공간으로 구성되어있다. 배열은 연속된 메모리 공간에 데이터를 저장 하기 떄문에,
배열을 생성할때, 크기를 미리 정해야한다. 동적으로 할당하면 중간에 메모리 공간이 부족할 수 있고, 연속된 공간을 확보 할 수 없어 서 배열을 늘릴수가 없다.


### Q2. `ArrayList.add(x)`를 호출하면 내부에서 무슨 일이 일어나나?
ArrayList 는 ADD 를 할경우 내부에서 현재 배열의 SIZE 를 확인하는 변수가 있어서 ,  그 변수로 사이즈를 확인한뒤 새로운 인덱스에 넣는다
따라서 O(1) 의 시간복잡도를 가진다.

### Q3. ArrayList가 꽉 차면 크기를 몇 배로 늘리나? 왜 매번 1칸씩 안 늘리나?
ArrayList 는 배열의 크기가 꽉차면 일반적으로 기존 사이즈의 1.5 배를 늘린다
매번 1칸씩 안늘리는 이유는 add 할때마다 배열을 새로만들고 기존 배열의 데이터를 복사하는 작업이 필요하기 때문에, 1칸씩 늘리면 성능이 매우 저하되기 때문이다. 따라서 일정 비율로 늘려서 복사 횟수를 줄이는 것이다.

### Q4. ArrayList는 왜 "중간 삽입/삭제"가 느린가?
중간에 삽입/삭제를 할경우  같은 배열 안에서 뒤 요소들을 한 칸씩 밀거나(삽입) 당기는(삭제) 작업 때문 O(n) 의 시간복잡도를 가진다. 따라서 중간 삽입/삭제는 느리다.

연속메모리라 고정 / size로 O(1) / grow는 가끔이라 평균 O(1)

## 추가 학습 (2026-08-02) — 분할상환(Amortized) 분석: "가끔 O(N)인데 왜 평균 O(1)인가"

> 대화 중 채팅으로 파고든 내용. Q&A로 도출한 뒤, 코치가 숫자로 검증해서 정리함.

### 핵심 구분: "그냥 O(1)" vs "분할상환(amortized) O(1)"
- **그냥 O(1)**: 매번 실행할 때마다 항상 일정하게 빠름.
- **분할상환 O(1)**: 개별 연산 하나만 콕 집으면 가끔 O(N)으로 튀지만(= grow가 일어나는 그 순간), **여러 번 실행한 비용을 전부 더해서 실행 횟수로 나눈 "평균"이 O(1)**이라는 뜻. `add()` 100번 중 99번은 진짜 O(1)이고 1번만 O(N)인데, 그 비싼 1번의 비용을 100번에 걸쳐 "분할해서 상환"한다고 보는 것.

### 숫자로 검증 (capacity 1.5배 성장, 1→2→3→4→6→9→13→19→28→42→63→94→141...)

원소 100개를 넣는다고 할 때, grow가 일어날 때마다 드는 복사 비용(= 그 순간 old capacity만큼 원소를 복사해야 함)을 전부 더하면:

```
1 + 2 + 3 + 4 + 6 + 9 + 13 + 19 + 28 + 42 + 63 + 94 = 284
```

여기에 실제로 100개를 넣는 기본 비용(1개당 1)까지 더하면 총 비용 ≈ 284 + 100 = **384**.

→ `add()` 100번 호출의 **총 비용 384 ÷ 100번 = 평균 3.84** → N(=100)이 아무리 커져도 이 평균값은 커지지 않고 **상수**로 수렴함. 이게 바로 amortized O(1)의 실체.

### 버스(좌석) 비유로 직접 손으로 세어보기 (N=10로 축소)

- **좌석 수(capacity)** = 배열이 몇 칸짜리인지. **탄 사람 수(size)** = 지금 실제로 몇 개 들었는지.
- **"꽉 찼다"** = 좌석 수 == 탄 사람 수일 때만.
- 꽉 차서 새 버스로 바꿀 때, 딱 1자리 더 큰 버스가 아니라 **기존의 1.5배 크기** 버스를 삼 → 그래서 새 버스엔 여분 좌석이 남을 때가 있음.

| 손님 | 상태 | 하는 일 | 결과(좌석/사람) |
|---|---|---|---|
| 1번째 | 좌석1,사람0 → 안참 | 그냥 태움 | 좌석1, 사람1 (꽉참) |
| 2번째 | 좌석1,사람1 → 꽉참 | 좌석2로 교체, 1명 옮김(복사1)+태움 | 좌석2, 사람2 (꽉참) |
| 3번째 | 좌석2,사람2 → 꽉참 | 좌석3로 교체, 복사2+태움 | 좌석3, 사람3 (꽉참) |
| 4번째 | 좌석3,사람3 → 꽉참 | 좌석4로 교체, 복사3+태움 | 좌석4, 사람4 (꽉참) |
| 5번째 | 좌석4,사람4 → 꽉참 | 좌석6(4의 1.5배)로 교체, 복사4+태움 | **좌석6, 사람5 → 여분 1석!** |
| 6번째 | 좌석6,사람5 → 안참(여분 씀) | 그냥 태움 (공짜) | 좌석6, 사람6 (꽉참) |
| 7번째 | 좌석6,사람6 → 꽉참 | 좌석9(6의 1.5배)로 교체, 복사6+태움 | 좌석9, 사람7 |
| 8번째 | 좌석9,사람7 → 안참 | 그냥 태움 (공짜) | 좌석9, 사람8 |
| 9번째 | 좌석9,사람8 → 안참 | 그냥 태움 (공짜) | 좌석9, 사람9 (꽉참) |
| 10번째 | 좌석9,사람9 → 꽉참 | 좌석13(9의 1.5배)로 교체, 복사9+태움 | 좌석13, 사람10 |

복사 비용만 뽑으면 `1+2+3+4+6+9 = 25`, 기본 태우기 비용 10(10명 전원)까지 더하면 총 `35` — N=10일 때 평균은 `35÷10=3.5`. **N=100일 때(284+100=384, 평균3.84)랑 똑같은 패턴**이라는 걸 작은 숫자로 직접 확인한 것.

### 등비수열(等比數列) 개념과 연결하기

**등비수열** = 매번 같은 비율(공비)을 곱해서 만드는 수열. 예: `2,4,8,16...`(공비2). 식: `n번째 항 = 첫째항 × 공비^(n-1)`.

- 위 표의 **좌석 수 시퀀스 `1,2,3,4,6,9,13...`가 바로 공비 1.5인 등비수열**이다 — "1.5배씩 커지는 버스"라는 말 자체가 등비수열이었던 것.
- 복사 비용을 **정방향**(1,2,3,4,6,9)이 아니라 **거꾸로**(9,6,4,3,2,1) 읽으면, 매번 `1/1.5 = 2/3`을 곱하는 **공비 2/3인 등비수열**이 된다. 같은 수열을 반대 방향에서 본 것뿐.
- 표의 "여분 좌석"(5번째 때 남긴 1석, 7번째 때 남긴 2석 등)이 바로 이 등비수열의 각 항에 해당한다.

**등비수열 합 공식**(공비 `r`이 1보다 작을 때): `합 = 첫째항 ÷ (1 - 공비)`.

여기에 대입: 공비 `r = 2/3`(=1/1.5), **첫째항은 실제로 손으로 센 "가장 큰 복사 비용"을 그대로 씀** (N=10 예시면 9 — 이걸 `2N/3` 같은 추상적 근사치로 억지로 안 바꿔도 됨, 그러면 오차만 커짐):

```
합 = 9 ÷ (1 - 2/3) = 9 ÷ (1/3) = 27   (실제 손계산 25와 거의 일치)
```

> ⚠️ 주의: "첫째항 ≈ 2N/3"이라고 근사해버리면 오차가 큼(N=100 예시에서 실제 마지막 복사는 94인데 2N/3=66.7로 꽤 차이남) — N이 좌석 경계선 어디에 걸리느냐에 따라 들쭉날쭉하기 때문. 그래서 실제 관측값을 첫째항에 넣는 게 더 정직함.

**근데 진짜 핵심은 정확한 배수(2배냐 3배냐)가 아님.** 공비가 2/3으로 고정이니 `합 = 첫째항 × 3`이 항상 성립하고, 첫째항은 항상 N과 같은 자릿수(N의 상수배 이내, 절대 N²처럼 폭증 안 함)이므로 **총합도 결국 "N에 비례하는 어떤 상수배"**라는 것만 중요함. 여기에 기본 삽입 비용 N을 더해도 총 비용은 여전히 O(N) → **N번 연산의 평균(1번당 비용) = O(N)/N = O(1)**. 정확한 상수(2N, 3N, 2.7N)에 집착할 필요 없이 "폭발 안 하고 N에 비례한다"는 사실 하나가 분할상환 O(1)의 본질.

### 실무 함정 (7년차 렌즈)
- 평균은 O(1)이어도 **딱 그 grow가 걸린 순간의 add() 하나는 진짜 O(N)** — 레이턴시에 민감한 시스템(예: 실시간 처리)에서는 "가끔 튀는 지연"으로 체감될 수 있음. GC pause와 비슷한 결의 문제.
- 넣을 개수를 미리 알 수 있다면 `new ArrayList<>(예상크기)`로 **초기 capacity를 지정**해서 grow(=복사) 자체를 원천 차단하는 게 실무 팁.

### 오늘 추가로 배운 것 3줄
개별 연산은 가끔 O(N)이어도 총합은 O(N) 수준 / 그래서 평균(분할상환)은 O(1) / 성장배수 r일 때 총 복사비용 ≈ N/(r-1)
